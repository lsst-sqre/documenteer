### Bug fixes

- `documenteer.ext.autotypes` no longer warns about the bare `FieldInfo` reference on Pydantic field pages. When a field's `Annotated[...]` metadata reprs into syntactically valid Python (any `Field(...)` without a lambda or enum default), Sphinx's annotation parser splits the rendered type into its parts and emits `FieldInfo` as a bare `py:class` reference — a name exposed by neither `pydantic` nor `pydantic.main`, so no existing resolution rung could reach it. Bare names are now looked up in the already-imported modules of the top-level packages the documented class's MRO comes from, which finds it in `pydantic.fields` and degrades it to unlinked literal text like the other external-object references. Names that several of those modules bind to different objects, and names none of them bind at all, stay unresolved so genuine typos keep warning.
- `documenteer.ext.autotypes` keeps module-level callable singletons — an instance of a `__call__`-defining class, the shape Safir's `*_dependency` injection helpers use — in Sphinx 9 builds. Sphinx 9 gives `data` objects no signature slot, but sphinx-autodoc-typehints computes a signature for any annotated callable, so Sphinx assigned into an empty list and swallowed the resulting `IndexError` as an `error while formatting signature` warning that dropped the object from the built documentation entirely. The extension now answers the `autodoc-process-signature` event ahead of sphinx-autodoc-typehints for `data` and `attribute` objects, so nothing supplies a signature Sphinx has nowhere to put and the object documents without a signature line, as Sphinx 9 renders data objects anyway.
- `documenteer.ext.autotypes` keeps non-field members — ordinary methods, classmethods, properties, and attributes — on autodoc-pydantic model pages in Sphinx 9 builds. autodoc-pydantic documents members through autodoc's legacy class-based API, which picks a documenter for each member out of the ones registered with autodoc; Sphinx 9 registers its own built-in documenters there only when `autodoc_use_legacy_class_based` is enabled, so autodoc-pydantic's field, validator, and config documenters were the whole candidate pool and every other member was silently skipped, taking prose references to it down as nitpick warnings. The extension registers the built-in documenters again, which restores the members without switching the build over to the legacy API — `autoclass`, `automethod`, and the rest still dispatch to Sphinx 9's native implementation, and a documenter another extension registered for the same object type is left in place. Projects that pinned `sphinx<9` in their documentation requirements over this can lift the pin.
- `documenteer.ext.autotypes` no longer warns about references to classes that a project defines only under its own private module paths. Pydantic field annotations routinely name a serialization model that lives in an internal module (`pkg._transforms._transform.MappingSerializationModel`) and is deliberately never re-exported; Sphinx 9 emits a `py:class` reference for it — as a bare name on the field's page, or as a fully-qualified name with no document context at all, reported from `<unknown>:1` — where Sphinx 8 rendered the same signature as unlinked plain text. Those objects import cleanly but can never have a public documentation target, so they now degrade to unlinked literal text like the external-object references beside them. The gate is the module path rather than the object: a project-local object degrades only when some segment of its defining module path starts with an underscore, so project-local objects under wholly public module paths — the ones that should be exported and documented but aren't — keep warning, as do names that fail to import at all.
- `documenteer.ext.autotypes` no longer warns about the reference targets Sphinx synthesizes out of a Pydantic field's `Annotated` metadata. The existing mangled-target rule catches a leaked `repr()` that cannot be Python at all; when the same rendering *does* parse, Sphinx splits it into syntactically clean fragments and emits a reference for each — the `annotated_types` constraint objects `Ge`/`Le` from a `FieldInfo` repr (`Field(ge=0, le=1)`), the unquoted string value `file` from Pydantic's `FilePath` (Sphinx renders dataclass metadata by stringifying each field value, so `PathType('file')` becomes `PathType(path_type=file)`), and enum members such as `ExecutionPhase.PENDING` written into the metadata of an annotation rendered from its source text. None of those name anything documentable, and the first two are not names of objects at all, so they now degrade to unlinked literal text. The rung rebuilds the fragments *that class's own* metadata renders and is consulted only after every resolution rung has already failed, so it resolves nothing and widens no lookup: a name no metadata rendering of the class contains — a typo of a real fragment included — keeps warning, and the annotated type itself keeps following the ordinary ladder.
- `documenteer.ext.autotypes` no longer warns about bare references to plain-assignment type aliases that belong to a package sharing the documented project's top-level root, such as `lsst.resources`'s `ResourcePathExpression = str | ParseResult | ResourcePath | Path` written into a documented `lsst.images` annotation. Sphinx 9 emits those as bare `py:class` references with no document context at all, reported from `<unknown>:1`, where Sphinx 8 rendered the same signature as unlinked plain text. Such an alias binds a bare union object that — unlike a PEP 695 `type` statement or a `TypeVar` — knows neither the name it was assigned to nor the module it was written in (its `__module__` reads `types`, or `typing` from Python 3.14 on), so the registry of typing objects scanned out of the project's package roots now records union aliases along with the module each one was found in, and a reference degrades to unlinked literal text only when every hit lies outside the project's documented module prefixes. An alias in one of the project's own modules keeps warning, because it should be documented as a `py:data` or `py:type` object instead — and once it is, the reference links rather than degrading. Every hit must also be the identical object, so a re-export chain resolves while one name meaning different unions in different modules keeps warning, as does a name no scanned module binds at all.
- `documenteer.ext.autotypes` now resolves bare references that come from docstrings inherited from external base classes, such as the bare `to_bytes` in `lsst.daf.butler`'s `FormatterV2.write_local_file` docstring, which `autodoc_inherit_docstrings` renders on any subclass that overrides the method without documenting it. Those names are attributes *of* an MRO class rather than names in any MRO class's module namespace, so no rung could reach them. The name is now looked up across the MRO's own attributes and retried against intersphinx as `{module}.{qualname}.{name}` of the class that defines it, which links to the base project's documentation when its inventory is configured and degrades to unlinked literal text when it is not. Names that are builtins are left alone (a bare `dict` means the builtin type, not `pydantic.BaseModel.dict`), and names no base class defines still warn.
