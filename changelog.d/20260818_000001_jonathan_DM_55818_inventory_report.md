### New features

- `documenteer.ext.intersphinxcache` now logs a summary block after prefetching intersphinx inventories, so a documentation author can see at a glance where each of their inventories came from. The block names every mapping entry the extension considered, in `intersphinx_mapping` order — the order the author sees in their own configuration file — with how that inventory was obtained: Ook's cache status passed through verbatim (`hit`, `stale`, `miss`), `served` when Ook answered but sent no cache-status header, `disk cache` for an entry reused from the client-side TTL fast path without contacting Ook at all, and `direct fetch` with the reason for an entry that fell back to a direct origin fetch. Entries the extension never prefetches — a local target URI, or an inventory location that is already a local path — get no row. The block is logged at info level, so a warnings-as-errors (`-W`) build is unaffected by it: none of what it reports is the author's to fix. The existing per-entry info lines are unchanged, and no prefetching behavior changed.

- Each Ook-served row in that block also reports when Ook last confirmed the inventory with its origin: the absolute UTC timestamp Ook sent, for correlating a row with Ook's own logs, plus a humanized relative age (`fetched 2026-08-18T17:58:24Z (26 minutes ago)`) for eyeballing how fresh the copy is. Note that this is when Ook last *confirmed* the inventory, not when the bytes it served were downloaded — a background refresh answered `304 Not Modified` keeps the stored bytes and still advances the time. The time rides Ook's `304` responses as well as its `200`s, so a build that holds current bytes and only revalidates still sees it. A row Ook served without a usable fetch time says `fetch time unavailable` rather than showing a placeholder that would read as an age, and a malformed timestamp from the service is treated the same way rather than being allowed to fail a build.

- When Ook reports that an intersphinx inventory URL has permanently moved, the build now says so. The entry gets its own info-level notice naming the mapping key, the URL the project configures, and the URL it now redirects to, followed by which of the author's *own* configuration files to change: `[sphinx.intersphinx.projects]` in `documenteer.toml` for a user guide, `[technote.sphinx.intersphinx]` in `technote.toml` for a technote, and `intersphinx_mapping` in `conf.py` for a project with neither file — so an author is never sent to edit a file their project does not have. The matching row in the summary block is flagged `-> moved`; the destination URL stays in the notice rather than widening every row. The notice rides Ook's `304` responses as well as its `200`s, so a build that only revalidates still sees it, and it is logged at info level, so a warnings-as-errors (`-W`) build succeeds with a permanent redirect present: the move originates upstream, outside the author's control. Note that Ook reports the redirect chain observed at *its* last successful fetch, which is why the flagged row is paired with that fetch time rather than presenting the move as current fact. Nothing about the prefetch changes — the mapping is still rewritten to the local cache file — and an older Ook that never sends the header behaves exactly as before.

- A project that would rather fail its build than carry a stale intersphinx inventory URL can now escalate that permanent-redirect notice to a Sphinx warning, which fails a warnings-as-errors (`-W`) build. Set `warn_on_permanent_redirect = true` under `[sphinx.intersphinx.cache]` in `documenteer.toml` for a user guide, or `documenteer_intersphinx_cache_warn_on_permanent_redirect = True` in `conf.py` for a technote — Documenteer adds no keys to `technote.toml`, whose schema belongs to the technote package. The default stays `false`, so nothing changes for a project that doesn't opt in. The setting escalates only that one notice: the inventory summary block stays at info level either way, so opting in never turns a block of pure status reporting into a build failure, and the mapping entry is still rewritten to the local cache file whether or not escalation is enabled. The escalated notice carries the warning subtype `documenteer.intersphinx_permanent_redirect`, so a project that already knows about one moved inventory can silence just that warning with `suppress_warnings = ["documenteer.intersphinx_permanent_redirect"]` and keep enforcement everywhere else.

### Other changes

- The `documenteer.toml` reference now documents the intersphinx inventory prefetch summary under `[sphinx.intersphinx.cache]`: an example of the rendered block, what every status it can show means (`hit`, `stale`, `miss`, `served`, `disk cache`, and `direct fetch`), and what the `-> moved` flag marks. It makes the operational point explicitly — a `stale` row on its own is a *normal* Ook serve rather than an error, because a copy past Ook's freshness lifetime is deliberately retained for availability while a background job revalidates it; it is `stale` paired with an *old fetch time* that means Ook's refreshes for that inventory have been failing, and that is the pairing worth reporting. It also spells out that the fetch time is when Ook last *confirmed* the inventory with its origin, not when the served bytes were downloaded.

- The technote configuration documentation now documents the intersphinx inventory cache settings a technote overrides in `conf.py` — `documenteer_intersphinx_cache_warn_on_permanent_redirect`, `documenteer_intersphinx_cache_use_service`, `documenteer_intersphinx_cache_service_url`, and `documenteer_intersphinx_cache_disk_cache_ttl` — so a technote author following the new permanent-redirect notice lands on a documented knob rather than an undocumented one. The new section also points technote authors at `[technote.sphinx.intersphinx]` in `technote.toml` for the Intersphinx *projects* they link to, and explains why the *cache* settings are `conf.py` values instead: Documenteer adds no keys to `technote.toml`, whose schema belongs to the technote package.

- The `documenteer.toml` reference is now scoped to user guides alone: its `[sphinx.intersphinx.cache]` section no longer carries an aside about how a technote configures the same prefetch. A technote does not read `documenteer.toml`, so that material belongs with the rest of the technote configuration documentation, which already states that a technote build logs the same summary block and gets the same permanent-redirect notice, and links back here for what they mean.
