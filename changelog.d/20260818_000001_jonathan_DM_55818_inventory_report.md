### New features

- `documenteer.ext.intersphinxcache` now logs a summary block after prefetching intersphinx inventories, so a documentation author can see at a glance where each of their inventories came from. The block names every mapping entry the extension considered, in `intersphinx_mapping` order — the order the author sees in their own configuration file — with how that inventory was obtained: Ook's cache status passed through verbatim (`hit`, `stale`, `miss`), `served` when Ook answered but sent no cache-status header, `disk cache` for an entry reused from the client-side TTL fast path without contacting Ook at all, and `direct fetch` with the reason for an entry that fell back to a direct origin fetch. Entries the extension never prefetches — a local target URI, or an inventory location that is already a local path — get no row. The block is logged at info level, so a warnings-as-errors (`-W`) build is unaffected by it: none of what it reports is the author's to fix. The existing per-entry info lines are unchanged, and no prefetching behavior changed.

- Each Ook-served row in that block also reports when Ook last confirmed the inventory with its origin: the absolute UTC timestamp Ook sent, for correlating a row with Ook's own logs, plus a humanized relative age (`fetched 2026-08-18T17:58:24Z (26 minutes ago)`) for eyeballing how fresh the copy is. Note that this is when Ook last *confirmed* the inventory, not when the bytes it served were downloaded — a background refresh answered `304 Not Modified` keeps the stored bytes and still advances the time. The time rides Ook's `304` responses as well as its `200`s, so a build that holds current bytes and only revalidates still sees it. A row Ook served without a usable fetch time says `fetch time unavailable` rather than showing a placeholder that would read as an age, and a malformed timestamp from the service is treated the same way rather than being allowed to fail a build.
