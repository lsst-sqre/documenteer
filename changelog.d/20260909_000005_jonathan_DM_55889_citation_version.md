### New features

- `[[project.citations]]` entries now carry a `version`, the release of the work being cited. It is set inline (`version = "12.3.0"`), or read from the `version` of whichever record a `CITATION.cff` file supplies the entry's fields from — the top-level record's, or a `preferred-citation`'s own. The version qualifies the title everywhere the citation is displayed (`Safir (version 12.3.0).`), is written as biblatex's `version` field on `@software` and `@dataset` entries, and reaches the JSON-LD as `softwareVersion` on a `SoftwareSourceCode` node and `version` on a `Dataset` node. The BibTeX key never carries it, so a reader's `.bib` file keeps working across releases. FORCE11's software citation principles list the version among the elements a software citation has to carry, and a citation of a package that names no release identifies the code that was run no more precisely than naming the language would.

- A software citation of this site's own package now names the version the site documents without restating it. A `software` entry that states no `version`, and whose `CITATION.cff` file supplies none, defaults to the site's own `project.version` — from `[project] version`, or from the installed distribution when `[project.python]` names one — when the entry is the `self` entry, the `preferred` citation, or reads a `CITATION.cff` file's top-level record with `cff_preferred = false`. Those are the three ways a site says an entry is the thing it documents; software the site merely cites is somebody else's package and is left version-less, and no other citation type ever defaults. A site that declares neither `project.version` nor `project.python` resolves its version to the literal `Latest`, which names a documentation build rather than a release and never reaches a citation. An explicit `version` always wins.
