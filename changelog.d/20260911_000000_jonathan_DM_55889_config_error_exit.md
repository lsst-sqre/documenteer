### Bug fixes

- A `documenteer.toml` or `technote.toml` that fails validation now ends the build with Documenteer's message and nothing else. The message itself was already written for whoever wrote the file, but every build printed it inside Sphinx's crash frame: a "Configuration error!" banner, a versions dump, an abridged traceback, the path of a saved traceback file, and an invitation to open an issue at `sphinx-doc/sphinx` — a report about Sphinx wrapped around a sentence about a typo. Sphinx renders that frame for *every* `SphinxError` raised while `conf.py` runs, branching on neither the exception's type nor its cause (`sphinx/_cli/util/errors.py:handle_exception`), and it re-raises a `sys.exit()` from `conf.py` as another one (`sphinx/config.py:eval_config_file`), so there is no cleaner exception and no ordinary exit that avoids it. Sphinx 7 printed a `SphinxError` as two lines with no traceback; the frame is a Sphinx 8 regression, and worth an upstream issue of its own. The configuration presets now print the message to standard error and terminate the interpreter directly, which is the one exit Sphinx does not intercept, so the build exits 2 with the message alone — with or without `-T`.

- A `technote.toml` that fails validation now names the field, the value, and the fix, instead of reporting `ConfigError: Syntax or validation issue in technote.toml` under a pydantic traceback that named nothing. The message is technote 0.12's own composition, written in the vocabulary a `documenteer.toml` is already reported in: `[technote] doi` followed by the sentence saying what a DOI looks like, `[technote.lint] ignore` followed by the sentence saying what a rule code looks like, `[[technote.authors]] author #1, affiliation #1, field ror` for a problem two arrays deep. Documenteer prints it as-is rather than re-composing it from the pydantic failure technote keeps as the error's cause, since only technote knows what one item of its own arrays is called. A `technote.toml` that TOML itself cannot parse is reported with the line and column the parser stopped at.

- A `[[project.citations]]` entry whose `type` is not one of the five kinds is now rejected in Documenteer's own words, which say what the five are and that a work that is none of them — an instrument or a facility, such as LSSTCam — is `"other"`. Pydantic's own sentence listed the members and stopped there.

- Configuration failures that are not validation failures — a `self` entry with no DOI, two citations sharing one BibTeX key, an unreadable `CITATION.cff` — now present identically to the ones that are, since they reach the same reporting path.

- None of this changes what a programmatic caller sees. `DocumenteerConfig.load()` still raises `ConfigError`, and the in-process technote read behind `documenteer technote lint` and `documenteer technote sync-cff` still gets an exception rather than an exit, so those commands finish their own reports. `sync-cff` gains the better message in the bargain: it used to relay `Syntax or validation issue in technote.toml`.

### New features

- New `documenteer.conf.raising_config_errors` context manager, for driving a Sphinx build in a process that has other work to do. A preset imported with an invalid `documenteer.toml` or `technote.toml` ends the interpreter — which is right for `sphinx-build`, whose process exists to run that one build, and wrong for a project's pytest fixture, a notebook, or a script, each of which would be terminated with status 2 and no traceback. Inside the block the failure is a catchable `ConfigError` instead. Documenteer's own in-process technote read uses it; the name is now public so anything else building a deliberately invalid root can too.
