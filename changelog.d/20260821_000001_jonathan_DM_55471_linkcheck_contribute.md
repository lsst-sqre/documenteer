### New features

- The link-check builder now contributes what its local recheck observed back to Ook. A build that settles a URL the service could only report as `blocked` knows something the service can't learn from its own vantage point, so those observations — successes and failures alike — are POSTed to the check's contributions endpoint, improving Ook's stored state for every project that references the same URL rather than just this one build's report. A URL that answered the build with nothing at all is withheld: an observation the build wouldn't apply to its own report has no business becoming shared evidence. So is an observation for a URL the service reported `broken` rather than `blocked` — the recheck covers those too, but Ook applies a contributed result only to a URL its own stored state has as `blocked`, so sending one would only earn a rejection. The contribution is attested by a GitHub Actions OIDC id token minted for the configured `service_url`, which scopes it to that one deployment; a workflow that wants to contribute therefore needs `permissions: id-token: write`, alongside the `OOK_TOKEN` that already authenticates it at the ingress. Outside GitHub Actions — a laptop build, or a workflow that never asked for that permission — the recheck still informs the build's own report and the contribution is skipped with an info-level note. Nothing about a contribution can fail a build: every outcome is reported at info level rather than as a warning, so a `-W` build can't fail on one either. Entries the service declines are reported per URL with their reason, and a contribution that cannot be delivered (after retrying the 502 the service documents as retryable), or one the service answers with a body this Documenteer release can't read, is reported and left at that. Setting `[sphinx.linkcheck] recheck_unverified = false` turns off the contribution along with the recheck.
